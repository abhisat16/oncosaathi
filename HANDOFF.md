## 1. Charter (what OncoSaathi must be)

- **Job:** tell cancer patients and caregivers *where to go, what to bring, what to pay, and their next step* inside a big hospital. Logistics only.
- **Never:** diagnosis, reading or interpreting reports, medicine names or doses, prognosis. Emergencies go to Gate 2 / 108. Clinical questions go to the nurse navigator. Fear or distress goes to the counsellor.
- **Users:** elderly, low-literacy, often out-of-state. Voice first (Hindi, Hinglish, English; Marathi next). Short answers: one step per turn, ≤30 words, with a landmark.
- **Grounding rule:** every direction must come from `hospital.json`. If it isn't there, say "I'm not sure" and send them to the help desk at Gate 1. **No invented rooms.** This is the main fix needed.
- **Channels:** WhatsApp-style web chat (text, voice note, slip photo) plus a live voice call. Real WhatsApp and phone (Exotel) come later.

## 4. Known problems (start here)

1. **The voice agent hallucinates.** It said Endoscopy is in "Radiology, ground floor"; per `hospital.json` it's Wing B, 2nd floor, B-201–B-204. Cause: the agent runs on **version 2, the old prompt**. The new prompt was pasted but **never committed** (only v1 and v2 exist). Also, the agent's LLM answers freely instead of looking facts up.
2. **Agent variables don't reach the agent's LLM.** The patient's name and next step are sent as `agent_variables` on every call, but the agent ignores them; the prompt probably uses typed `{var}` text instead of `@` chips. With the long greeting removed, calls are no longer personalised.
3. **SDK default version.** Without a version number, the SDK calls the *deployed* version (v1), not the newest commit. `server.py` works around this by detecting the newest committed version on each call.
4. The machine-translated Hindi in `hospital.json` (`*_hi` fields) needs a human skim.
5. **Security:** the main Sarvam key was pasted in chat twice. Rotate it.

## 5. Suggested plan for the rebuild

1. Stop relying on the agent's own LLM knowledge for directions. Choose one:
   - **(a)** Give the Sarvam agent a **tool or API call** (e.g. `GET /api/lookup?q=`) that returns the matching `hospital.json` entry, and instruct it to *always* call the tool before giving a direction. Or
   - **(b)** Run the call pipeline ourselves: streaming STT → `core.answer()` → `bulbul:v4-flash` streaming TTS. That is fully grounded and needs no agent console.
2. Keep the prompt short: persona, safety and "use the tool". Not 12K characters of facts.
3. Pass patient context properly: tool lookup by UHID, or correctly configured agent variables.
4. After each change: commit in Samvaad, check that a new version number exists, and run a call test with known answers (Endoscopy → Wing B 2F; PET-CT → Wing C basement; "tez bukhar after chemo" → Emergency).

## 6. Voice agent rebuild (done 18 Oct 2026, evening)

The 📞 call no longer uses the hosted Sarvam agent. It runs our own pipeline (option b), so it can't invent rooms.

```
browser mic (16 kHz PCM) → /ws/call → voice_call.py: energy VAD + barge-in
  → saaras:v4 STT (codemix) → brain.py → bulbul:v4-flash TTS (sentences in parallel) → browser
```

- **brain.py:** safety keywords (core.py) run first and can't be overridden. Then `sarvam-105b` (thinking off, ~0.4 s) only **classifies** the words into one label: a `hospital.json` id, or EMERGENCY / CLINICAL / EMOTIONAL / NEXT_STEP / FOLLOWUP / SCAN_GENERIC / OPD_GENERIC / GREETING / BYE / NONE. Any label that isn't in the file is rejected. The spoken words come from templates filled from `hospital.json`. If the LLM fails or rate-limits, the core.py rule matcher decides; if nothing matches: "ask at the help desk at Gate 1".
- **Call memory:** the last place discussed, so "wahan kya lana hai" / "timing kya hai" work. "पेट सीटी" is ambiguous (PET-CT or a stomach CT), so the agent names both rooms.
- **Personalised:** greets the selected patient by name; "mera agla step" reads their record.
- **Rollback:** `CALL_ENGINE=sarvam_agent` brings back the old hosted agent. Backups: `server.before_voice_rebuild.bak.py`, `core.before_voice_rebuild.bak.py`.

**Tests (run both after any change to hospital.json, core.py or brain.py):**
- `.venv/bin/python eval_brain.py`: 41 labelled questions (Hindi, Hinglish, English, safety, follow-ups). It also fails if a reply mentions a room that isn't in hospital.json. Last runs: 41/41, 40/41, 41/41 (the LLM has a little randomness).
- `.venv/bin/python call_test.py`: synthesises spoken questions, streams them through `/ws/call` like a real call, and checks the replies and barge-in. Last run: all passed.

**Latency:** 2.2–5.4 s from the end of speech to the first audio, plus 0.75 s of silence detection. Sarvam STT varied between 0.5 and 2.7 s and TTS took about 0.8–1.9 s. Next speed-up: streaming STT/TTS (`speech_to_text_streaming`, `text_to_speech_streaming` in the `sarvamai` SDK).

**Still open:**
- Roman "dawai kahan milegi" hits the CLINICAL keyword `dawa`, so it goes to the nurse when it should go to the pharmacy. That's safe but annoying; the keyword list needs a decision.
- Two Hindi mistranslations fixed (attendant ≠ परिचारिका, in Endoscopy `bring_hi` and the surgical ward `note_hi`). The rest of the `*_hi` text still needs a human skim.
- Registration (counters 1–6) and Billing (counters 1–4) are both in the "main lobby" with overlapping counter numbers in `hospital.json`.
- Not yet tested with a real microphone (the Claude app's browser blocks the mic). Test from the gradio.live link in Chrome.

## 10. Real WhatsApp channel (22 Oct 2026, Twilio Sandbox)

- **Flow:** phone → Twilio → `POST /whatsapp/twilio` (server.py) → we answer Twilio at once with empty TwiML, then in the background: voice note (OGG/Opus) → `saaras:v4` STT → `brain.respond()` (same grounded brain as the web chat) → text reply + the same words as a voice note. TTS asks Sarvam for `output_audio_codec="opus"` (`core.tts(text, lang, "opus")`), which is WhatsApp's own voice-note format, so no ffmpeg is needed. The voice note is held in memory for 30 min at `/wa/audio/<random>.ogg` for Twilio to fetch; nothing is written to disk.
- **Consent (DPDP):** a new number can ask for directions right away (answered from hospital.json, nothing stored) and is asked once to reply "हाँ"/"yes". Only then `patient_store.create(consent=True)` runs and the opening flow starts. "नहीं" = never asked again. "delete" / "मेरा डेटा मिटाओ" erases the person. A slip photo is only processed after consent. Logs show the route and the last 2 digits of the number only.
- **Security:** every webhook must carry a valid `X-Twilio-Signature` (403 otherwise). Media is only downloaded from `api.twilio.com`.
- **Files:** `whatsapp.py` (Twilio send/verify/media, audio cache, Meta Cloud API migration notes), the WhatsApp block in `server.py`, `wa_test.py`. Backups: `server.before_whatsapp.bak.py`, `core.before_whatsapp.bak.py`.
- **Set-up (once):**
  1. twilio.com → sign up → Console → Messaging → Try it out → *Send a WhatsApp message*. From your phone, send the shown `join <two-words>` code to +1 415 523 8886.
  2. Put `TWILIO_ACCOUNT_SID` and `TWILIO_AUTH_TOKEN` in `.env` (placeholders are there).
  3. Restart: `pkill -f frpc_darwin; SHARE=1 .venv/bin/python server.py`. It prints `* WhatsApp webhook ...: https://<id>.gradio.live/whatsapp/twilio`.
  4. Sandbox settings → *When a message comes in* = that URL, method POST → Save.
  5. Send "एंडोस्कोपी कहाँ होती है?" (text or voice note) → text + voice note: Wing B, second floor, B-201–B-204.
- **Sandbox limits:** each tester must send the join code first (it lapses after 72 h); only people who joined can chat. If the gradio link changes, update the webhook URL (or set `PUBLIC_URL`).
- **Tests:** `wa_test.py` 14/14 (signed fake webhooks, real Sarvam STT/brain/TTS, Twilio sending mocked). `eval_brain.py` 39/39.
- **Meta WhatsApp Cloud API later:** only `whatsapp.py` and the webhook route change: GET verify-token handshake + JSON webhook, `X-Hub-Signature-256` check, media via Graph API with the Bearer token, upload the Ogg/Opus to `/media` and send `{"type":"audio","audio":{"id":…}}`. Free-form replies only within 24 h of the patient's last message; reminders need the approved template (already in `reminders.py`). Needs a Meta Business account, a verified number and display-name approval.
